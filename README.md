## 1. 视频服务系统架构与实现
目前项目已完成视频服务子系统的核心开发，基于 i.MX6ULL 嵌入式 Linux 平台，实现了摄像头图像采集、跨进程数据共享、本地 LCD 显示及浏览器远程实时预览。
系统采用多进程架构，将硬件设备管理与网络业务处理分离，主要由 Camera Service 和 Web Service 两个独立进程组成。

#### 1.1. 服务架构设计
Camera Service 负责摄像头设备管理和原始图像采集，Web Service 负责图像显示、JPEG 压缩、HTTP 请求处理及网络视频推流。
两个进程之间采用控制与数据分离的通信方式：
- 控制通道：基于 Unix Domain Socket 实现进程间通信，用于摄像头启停控制、设备状态查询等操作。
- 数据通道：基于 POSIX 共享内存构建图像帧环形缓冲区，实现摄像头采集进程与业务进程之间的图像数据共享。

通过将控制指令与大容量图像数据分别传输，避免使用 Socket 反复传递完整图像帧，减少跨进程数据复制开销，同时降低摄像头采集模块与上层业务之间的耦合。

#### 1.2. 视频采集与图像处理
摄像头采用 OV5640 图像传感器，通过 Linux V4L2 接口完成设备访问与视频采集。
采集模块使用 V4L2 MMAP 方式申请并映射视频缓冲区，由驱动管理图像数据的填充，用户空间通过缓冲区出队与重新入队完成连续采集。
采集到的 RGB565 图像写入共享内存环形缓冲区，供其他服务读取，实现采集与后续图像处理的解耦。

针对不同的图像输出需求，系统采用两条处理路径：
- 本地显示：通过 Linux Framebuffer 将 RGB565 图像输出到 LCD，实现摄像头画面的实时预览。
- 网络传输：将 RGB565 图像转换为 RGB888，再通过 libjpeg 压缩为 JPEG 格式，用于浏览器端 MJPEG 视频流传输。

这种方式使原始图像能够同时服务于本地显示和远程预览，而无需分别打开摄像头设备。

###### HTTP 服务与多客户端视频推流

**1. 轻量级 HTTP 服务**
Web Service 基于 Linux TCP Socket 实现轻量级 HTTP 服务器，负责接收客户端连接、解析 HTTP 请求，并根据请求路径分发相应操作。
目前提供以下接口：

| 请求方式 | 接口 | 功能 |
| :--- | :--- | :--- |
| GET | /api/status | 查询摄像头运行状态、分辨率、像素格式及帧率 |
| POST | /api/start | 启动摄像头采集 |
| POST | /api/stop | 停止摄像头采集 |
| GET | /api/stream | 建立 MJPEG 视频流连接 |

普通控制请求采用 JSON 格式返回处理结果；视频流请求则保持 HTTP 连接，通过持续发送图像帧实现实时预览。

**2. MJPEG 视频流传输**
视频流采用 MJPEG（Motion JPEG） 方案，通过 HTTP multipart/x-mixed-replace 响应连续传输 JPEG 图像。
每一帧图像均作为独立的 multipart 数据段发送，包含相应的内容类型、数据长度及 JPEG 图像数据。浏览器通过 <img> 元素即可接收并显示连续画面，无需额外的视频解码组件。
相较于复杂的视频编码与流媒体协议，该方案实现简单，便于在资源受限的嵌入式平台上部署，并可直接与 Web 页面集成。

**3. 多客户端并发推流**
为支持多个浏览器客户端同时预览视频，系统采用“单压缩线程、多上传线程”的并发模型。
JPEG 压缩线程负责从共享内存获取图像帧并生成压缩数据，多个客户端上传线程共享最新的 JPEG 帧，各自通过独立的 TCP 连接向浏览器发送数据。
线程间使用互斥锁保护共享帧缓冲区，并通过条件变量协调新帧的发布与消费。客户端连接由链表统一管理，支持动态添加和移除。
该设计避免为每个客户端重复执行 JPEG 压缩，将图像处理与网络发送解耦，使不同客户端能够独立进行数据传输。

**4. 线程同步与连接管理**
在多客户端推流过程中，网络发送速度可能受到浏览器接收能力、TCP 缓冲区及网络状态影响，导致 send() 阻塞。
为避免慢速客户端影响整个视频处理链路，上传线程在互斥锁保护下复制当前 JPEG 帧，并在释放锁后执行网络发送，防止阻塞式 Socket 操作长期占用共享帧缓冲区的互斥锁。
同时，针对客户端连接关闭、视频服务停止和线程回收等场景，对线程同步、条件变量等待及资源释放流程进行了调试和完善。
目前已实现从摄像头采集到本地显示、HTTP 控制及多客户端 MJPEG 预览的完整视频处理链路，视频服务子系统的主要功能已基本完成。

## 2. web 服务端及客户端
web 服务是位于最顶层的应用，主要负责：
- 使用 camera 客户程序，控制摄像头开关、获取摄像头配置、获取摄像头数据等操作；
- 使用 display 程序，实时显示拍摄图片；
- 接收 web 客户端发送的 api 请求，进行对应的控制操作：获取摄像头状态、拍摄图片本地显示开启/关闭、拍摄图片上传给 web 客户端显示等。

**使用方法**
唤起主程序后，camera 服务和 web 服务都会被开启。此时全部操作都由 http 请求实现，此程序因此实现了一套 web ui，方便用户交互控制。web ui 程序在项目的 /web 目录下。开启服务有如下两种方式：
1. 输入如下命令：
```shell
cd web
python3 -m http.server 8000
```
然后在浏览器中打开：http://localhost:8000/index.html

这相当于有两个服务器，一个是 python 的 http 服务器，另一个是开发板的 C http 服务器。在浏览器打开上述网址后，python 会把 HTML、JS、CSS 文件提供给浏览器。在浏览器上通过 app.js 发送的请求会直接发送给开发板。

2. 类似方式 1，但是在开发板上开启另外一个 http，向 web 客户端提供页面资源：
首先需要确保 HTML、JS、CSS 文件都在开发板下，输入如下命令开启 http 服务(web 文件路径改为自己保存的路径):
```shell
httpd -f -p 8000 -h /path/to/web/
```
这里的端口不能与 C http 的端口(16767)相同。
然后在浏览器中打开：http://192.168.0.50:8000/index.html

192.168.0.50是我的开发板的IP，根据自己的情况调整。

> index.html 不要用 file:// 协议打开，因为这样在开启网络视频流时，浏览器会升级跨来源图片请求，将请求转为TLS握手。而现有的服务程序只支持 HTTP 请求，这就导致了失败。而使用方法 1 的打开方式可行，是因为该方式下，页面文件的来源是 http，浏览器会根据页面来源和安全策略决定如何处理 JS 发起的资源请求。

#### web 目录结构
- app.js: web 后端程序
- index.html: web ui 页面
- style.css: 页面样式文件
